# mcp-hpc-runner 设计说明书

## 项目概述

`mcp-hpc-runner` 是一个本地 Python 服务，将 HPC 执行能力以 MCP 工具接口的形式暴露出来。它支持两种执行后端：

- **SSH 直连**：用于轻量级同步命令
- **Slurm sbatch**：用于长时异步 HPC 作业

项目在本地与远端之间暂存文件、维护每次 run 的制品存储、验证期望输出，并为同步和异步操作返回统一的结果信封。

### 两种使用方式

1. **作为真正的 MCP 服务器**（stdio JSON-RPC）：通过 `serve` 启动，连接任何支持 stdio transport 的 MCP 客户端。
2. **作为本地调试 CLI**：通过 `list-tools` 查看工具表面，通过 `call-tool` 直接调用工具，无需 MCP 客户端。

## 设计原理

### 1. 核心数据模型：RunSpec

一切围绕 `RunSpec` 展开——调用方提交一个声明式的任务描述：

```
RunSpec {
  name, stage, command[]        # 任务标识 + 要执行的命令
  execution_mode                # "ssh" | "sbatch" | "auto"
  resources: ResourceSpec       # cpus, mem_mb, gpus, time_minutes, partition
  inputs: StagedInput[]         # 本地→远端文件映射
  expected_outputs[]            # 期望产出的文件（file | dir）
  success_checks[]              # 成功验证规则（exists | non_empty | json）
  failure_signatures[]          # 失败模式匹配（正则 → 错误码）
  fallback[]                    # 降级策略
  metadata{}                    # 透传元数据
}
```

公开 `RunSpec` 不包含 `run_id`。`server.py` 在接受请求后分配随机 opaque
`run_id`，再把它写入内部模型和持久快照；调用方显式提供该字段会被拒绝，
不会作为幂等键使用，也不会被静默覆盖。

所有模型均为纯 `dataclass(slots=True)`，通过 `from_dict` / `to_dict` 与 JSON 序列化层对接，无外部依赖。

### 2. 执行模式自动选择（mode.py）

`auto` 模式下按资源需求自动判断，优先级如下：

```
gpus > 0                               → sbatch
time_minutes >= slurm.time_threshold   → sbatch（默认 60 分钟）
mem_mb >= slurm.mem_threshold          → sbatch（默认 32768 MB）
其他                                   → ssh
```

这使 AI 调用方不需要关心集群拓扑，只需声明资源需求，系统自动路由。

### 3. 双后端架构

| 后端 | 适用场景 | 返回行为 |
|------|---------|---------|
| `SSHRunner` | 轻量同步任务 | 内部同步 `RunResult`（含完整 stdout/stderr）；公开终态不携带 inline 日志，仅投影闭集状态/错误字段 |
| `SlurmRunner` | 长时异步 HPC 作业 | 内部 `RunResult` 持有 raw handle；公开响应仅含 `run_id` 与状态 |

**Slurm 异步工作流**是典型的"提交 → 轮询 → 取回"模式：

```
job.submit({runspec})                 →  {run_id, status="submitted", ...}
job.status({run_id})                  →  {run_id, state=...}
job.logs({run_id, tail_lines?})       →  有界日志内容
job.fetch_artifacts({run_id})         →  声明产物引用 + 验证状态
job.cancel({run_id})                  →  取消状态
```

`job_id`、`remote_run_dir`、`job_handle.json` 内容和 sbatch 路径仅供 runner
内部使用。生命周期工具不接受 raw handle；`fetch_artifacts` 也不接受 inline
RunSpec，而是从同一个 run 的持久快照恢复声明。

### 4. MCP 协议层（server.py）

实现精简的 JSON-RPC 2.0（stdio transport）：

- `initialize`：握手，返回 serverInfo + capabilities
- `tools/list`：返回工具描述列表
- `tools/call`：路由到 `call_tool()`，结果包装为 MCP content envelope

`call_tool()` 是纯分发路由，无业务逻辑，所有实现下沉到各 runner 模块。同时支持 CLI `call-tool` 模式，绕过 MCP 客户端直接调试。

### 5. 错误规范化（errors.py）

`FailureMapper` 将 stderr 文本与用户自定义 `failure_signatures`（正则 + 错误码）匹配，返回结构化的 `error_code`，使上层（AI agent）可以程序化处理失败原因，而不是解析自由文本。

## 文件 Staging 详解（staging.py）

### 上传流程

```
本地文件                   StagingManager.upload_inputs()
    │
    ├─ SHA-256 计算（_sha256）
    │    ├─ 文件：逐块读 1MB，滚动哈希
    │    └─ 目录：按路径排序递归哈希（结构 + 内容）
    │
    ├─ 查缓存 input_dedup.json
    │    key = "sha256:remote_path"
    │    命中 → skipped=True，跳过传输
    │
    ├─ 未命中 → 上传
    │    ├─ 先 ssh mkdir -p <remote_parent>
    │    ├─ 尝试 rsync -az --partial -e "ssh -o BatchMode=yes"
    │    │    ↓ 失败（如集群没装 rsync）
    │    └─ 降级 scp -o BatchMode=yes [-r]
    │
    └─ 更新缓存 + 写 inputs_manifest.json
```

**远端路径规则**：所有输入落在 `<remote_run_dir>/work/<remote_path>`，`remote_path` 必须是相对路径（validation.py 会拒绝绝对路径）。

### 下载流程

```
StagingManager.download_outputs()
    │
    ├─ 从远端 <remote_run_dir>/out/<expected.path> 下载
    ├─ 落到本地 <artifact_root>/<run_id>/outputs/<expected.path>
    ├─ 同样优先 rsync → 降级 scp
    └─ 写 outputs_manifest.json（含每条 returncode）
```

注意：下载**不做去重缓存**，每次 `fetch_artifacts` 都全量重新拉取（输出文件可能被 Slurm 作业持续写入）。

### 去重缓存设计细节

```json
// <repo>/.mcp_hpc_runner/artifacts/cache/input_dedup.json
{
  "abc123...def:mcp_runs/run001/work/input.pdb": "mcp_runs/run001/work/input.pdb"
}
```

- **key**：`SHA256:remote_path`（内容 + 目标位置双维度，remote_path 含 run_id，因此是 run 级别去重）
- **value**：上次成功传输的远端路径（与传输命令一致，可能是绝对路径或相对 home 的路径）
- **语义**：相同内容传到相同位置 → 跳过。同一文件传到不同目录（不同 run），key 不同，仍然传输。

### 远端目录结构

每次 run 在远端创建固定布局：

```
<remote_base_dir>/<run_id>/
├── work/    ← 输入文件（命令的工作目录）
├── out/     ← 期望输出文件（命令应写入此处）
├── tmp/     ← 临时文件
└── logs/    ← Slurm 日志（slurm-%j.out / slurm-%j.err）
             ← 以及上传的 job.sbatch 脚本
```

## 本地制品存储详解（store.py）

### 本地目录布局

```
<repo>/.mcp_hpc_runner/artifacts/
├── cache/
│   └── input_dedup.json              ← 全局共享的上传去重缓存
│
└── <run_id>/                          ← run_id = 完整 128-bit UUID hex
    ├── inputs/                        ← 暂未使用（占位）
    ├── outputs/                       ← 下载回来的产出文件
    ├── logs/
    │   ├── stdout.log                 ← SSH 模式：命令 stdout
    │   ├── stderr.log                 ← SSH 模式：命令 stderr
    │   └── slurm_tail_stdout/stderr.log  ← Slurm 模式：job.logs 拉取的 tail
    └── metadata/
        ├── runspec.json               ← 原始 RunSpec 快照
        ├── run_result_metadata.json   ← Host-private 执行元信息（时间戳、状态、exit/error/stage、校验结果）
        ├── inputs_manifest.json       ← 上传清单（路径、哈希、是否跳过）
        ├── outputs_manifest.json      ← 下载清单（路径、returncode）
        │
        │   # Slurm 模式额外产出：
        ├── job_handle.json            ← job_id + remote_run_dir（跨会话恢复用）
        ├── submit_metadata.json       ← sbatch 提交元信息
        └── job.sbatch                 ← 生成的 sbatch 脚本副本
```

### ArtifactStore 的实现选择

`ArtifactStore` 故意做得极简（不用 SQLite / 不用数据库）：

| 操作 | 实现 |
|------|------|
| `write_json` | 写到 `metadata/<name>.json`，`sort_keys=True` 保证 diff 稳定 |
| `read_json` | 从 `metadata/<name>.json` 读，用于跨会话恢复 handle |
| `write_log` | 写到 `logs/<name>`，纯文本 |
| `ensure_run_layout` | 幂等 `mkdir -p`，多次调用安全 |
| `load/save_dedup_cache` | 直接读写 `cache/input_dedup.json`，单线程假设，无锁 |

### 跨会话恢复机制（job_handle.json）

Slurm 作业是异步的，AI agent 提交后会话可能中断，下次需要恢复轮询。恢复链路：

```
第一次调用 job.submit
  └─ 写 metadata/job_handle.json
       { "run_id": "...", "job_id": "12345", "remote_run_dir": "...", "submitted_at": "..." }

N 分钟后，新会话调用 job.status(run_id="...")
  └─ server._load_handle(run_id)
       └─ slurm_runner.load_handle(run_id)
            └─ store.read_json(run_id, "job_handle.json") → JobHandle 对象
```

公开调用只需要 `run_id` 就能恢复，不依赖进程内内存。服务重启后仍从
ArtifactStore 读取 handle；缺失记录、记录内 run_id 不一致、目录与配置根
不一致都会 fail-closed。旧的 `job_id + remote_run_dir` 恢复方式已退役。
同步 SSH 在单次调用中返回终态，因此只持久化 `runspec.json`，不会生成
可恢复的 `job_handle.json`；Slurm 异步提交则必须把同一 `run_id` 同时绑定到
`runspec.json` 和 `job_handle.json`。

## 输出验证机制（validation.py）

下载产出后，`fetch_artifacts` 做三层检查：

### 第一层：结构性检查（validate_expected_outputs）

| 情况 | 结果 |
|------|------|
| `required=True` 但文件/目录不存在 | → `missing_outputs` |
| `non_empty=True` 但文件大小为 0 / 目录为空 | → `empty_outputs` |

### 第二层：语义检查（run_success_checks）

由 RunSpec 的 `success_checks` 字段声明，支持三种类型：

| check_type | 验证内容 |
|-----------|---------|
| `exists` | 路径必须存在 |
| `non_empty` | 文件非空 / 目录有内容 |
| `json` | 文件存在且是合法 JSON（`json.loads` 不抛异常） |

### 第三层：失败签名匹配（FailureMapper）

对 stderr 文本做正则匹配，将已知的失败模式映射为结构化的 `error_code`：

```json
// RunSpec.failure_signatures 示例
[
  { "pattern": "CUDA out of memory", "error_code": "GPU_OOM" },
  { "pattern": "DiskQuotaExceeded",  "error_code": "DISK_QUOTA" }
]
```

### 最终状态判定

```
任一层失败  →  status="failed", error_code="OUTPUT_VALIDATION_FAILED"
全部通过    →  status="completed"
```

这套机制让 AI agent 不需要自己写文件检查逻辑，在 RunSpec 里声明期望即可。

## SSH 执行后端流程（ssh_runner.py）

```
SSHRunner.exec_run(spec)
    │
    ├─ 1. ensure_valid_runspec(spec)       — 前置校验
    ├─ 2. 使用 server 已分配的 run_id，创建本地目录布局
    ├─ 3. store.write_json("runspec.json") — 持久化快照
    ├─ 4. ssh mkdir -p <remote_run_dir>/{work,out,tmp,logs}
    ├─ 5. staging.upload_inputs()          — 上传输入文件
    ├─ 6. 构造远端命令：
    │      bash -lc "cd '<work_dir>' && <command>"
    │      ssh -o BatchMode=yes <target> -- <remote_argv>
    ├─ 7. 执行，捕获 stdout/stderr，脱敏
    ├─ 8. store.write_log("stdout.log" / "stderr.log")
    ├─ 9. 仅 remote exit=0 且未发生 requested identity failure 时
    │      staging.download_outputs()      — 下载声明产出（如有）
    ├─ 10. 先保留 raw nonzero transport/tool failure，再做成功态三层输出验证
    ├─ 11. store.write_json("run_result_metadata.json")
    └─ 12. 内部返回 RunResult；server 不投影 inline 日志，只返回必要的闭集状态
```

成功态 identity marker 缺失或非法只在 raw exit 为零时映射为
`TOOLCHAIN_IDENTITY_MISSING`；remote nonzero 必须保留原始 transport/tool error，
并跳过 output fetch。完整 stdout/stderr 与 `remote_command` 只存在于
Host-private artifact store；agent-facing server/adapter/engine 结果不得携带这些字段。

## Slurm 提交后端流程（slurm.py）

### 提交阶段（job.submit）

```
SlurmRunner.submit(spec)
    │
    ├─ 1. ensure_valid_runspec(spec)
    ├─ 2. 使用 server 已分配的 run_id，创建本地 + 远端目录布局
    ├─ 3. store.write_json("runspec.json")
    ├─ 4. staging.upload_inputs()
    ├─ 5. 生成 sbatch 脚本（build_sbatch_script）：
    │      #!/usr/bin/env bash
    │      set -euo pipefail
    │      #SBATCH --job-name=...
    │      #SBATCH --cpus-per-task=...
    │      #SBATCH --mem=...
    │      #SBATCH --time=...
    │      #SBATCH --output=<remote_run_dir>/logs/slurm-%j.out
    │      #SBATCH --error=<remote_run_dir>/logs/slurm-%j.err
    │      #SBATCH --partition=...（如有）
    │      #SBATCH --gpus=N 或 --gres=gpu:N（按 gpu_flag_style）
    │      export WORKDIR/OUTDIR/TMPDIR/LOGDIR/...（布局提示）
    │      cd '<work_dir>'
    │      bash -lc "cd '<work_dir>' && <command>"   ← login shell（与 SSH 模式对齐）
    ├─ 6. 上传 job.sbatch 到远端
    ├─ 7. ssh sbatch --parsable <remote_script>  → 解析 job_id
    ├─ 8. store.write_json("job_handle.json")    — 持久化 handle
    └─ 9. 内部返回含 job_id 的 RunResult；公开仅返回 opaque run_id
```

### 状态查询（job.status）

```
squeue -h -j <job_id> -o %T
    ↓ 无输出（作业已结束，离开队列）
sacct -j <job_id> --format=State,ExitCode --parsable2 --noheader

原始 Slurm 状态 → 规范化状态映射：
  PENDING / CONFIGURING / REQUEUE_FED  → "queued"
  RUNNING / COMPLETING                 → "running"
  COMPLETED                            → "completed"
  CANCELLED / PREEMPTED                → "cancelled"
  FAILED / TIMEOUT / OUT_OF_MEMORY / NODE_FAIL → "failed"
```

## 整体设计哲学

**把 HPC 的复杂性封装成声明式工具接口**。

AI agent 只需提交 `RunSpec`（声明资源需求、输入输出、验证规则），系统负责：

- 自动选择 SSH 或 Slurm
- 文件传输（含去重）
- 生成 sbatch 脚本
- 跨会话持久化状态
- 输出验证与错误码规范化

Agent 不需要了解 SSH 批处理模式、rsync 参数、squeue/sacct 的差异、Slurm 状态枚举——这些复杂性全部由 runner 层吸收。
