## Context

Phase 1 已经把 Host 的主流程搭起来了：系统能启动 workflow、选择动作、执行工具、记录审计、等待反馈、再从中断点恢复。现在真正缺的不是“能不能做”，而是“用户能不能看懂系统在做什么、为什么这样做、什么时候该停、自己接下来该做什么”。

这次变更是一个跨模块的体验补全：

- `packages/enzyme-host-runtime` 负责把“停下原因、下一步建议、审批依据、决策解释、进度摘要”整理成规范状态。
- `apps/enzyme-web-host` 负责把这些状态变成浏览器里易读、易介入的界面。
- `apps/enzyme-host-cli` 负责在终端里用简洁文本给出同样的信息。
- `apps/mcp-project-memory` 继续承担规范状态真源，避免 Web 和 CLI 各自维护私有解释或私有进度。

约束也很明确：

- 这次先补“决策体验”，不顺手扩成新的 MCP 能力开发。
- 文档和状态命名要尽量通俗，优先让人看懂，不追求学术化术语。
- 解释、进度和审批理由必须由 runtime 统一生成，不能让不同界面各说各话。

## Goals / Non-Goals

**Goals:**

- 让 Host agent 在每个关键节点都能明确表达“现在处于什么状态”。
- 让用户能快速知道“为什么停在这里”和“下一步最合理的动作是什么”。
- 让审批/信任策略从“隐藏逻辑”变成“可解释规则”。
- 让 Web Host 和 CLI 读取同一份进度、解释和停止原因，而不是各自拼装。
- 为后续 `mcp-bio-research`、`mcp-structure-workbench` 和多轨设计打一个更稳的体验底座。

**Non-Goals:**

- 不在这次设计里引入新的 MCP server。
- 不在这次设计里实现多轨设计、候选多样性控制或复杂评分系统。
- 不承诺精准剩余时间预测；首版只提供“阶段感”和“下一步提示”。
- 不把 Web Host 做成重前端产品；继续复用现有 shared runtime 和 server-rendered 思路。

## Decisions

### 1. 由 runtime 生成统一的“决策体验摘要”，而不是让各界面自己推断

决定：

- 在 canonical agent state 或等价规范状态里增加一组面向体验的结构化字段，例如：
  - 当前阶段或当前卡点
  - 停止原因
  - 下一步建议
  - 用户是否需要介入
  - 简明解释
  - 技术解释

原因：

- 这样 Web 和 CLI 才能共享同一份语义。
- 这样测试也可以直接验证 runtime 输出，而不是分别测两个界面的文案拼装。

备选方案：

- 让 Web Host 和 CLI 各自基于原始状态自行推导解释和进度。

不选原因：

- 很容易出现同一 episode 在两个入口显示不同结论。
- 后续一旦加入更多 capability 或 workflow 分支，界面层推断会越来越脆弱。

### 2. 解释分成“两层”，主界面优先说人话

决定：

- 每个关键决策和停止点都提供两种解释：
  - `plain_language_explanation`：面向普通用户，说明发生了什么、为什么重要、建议怎么做；首版固定使用中文
  - `technical_explanation`：面向调试和审计，说明触发条件、相关状态、预算或策略原因

原因：

- Phase 2 的核心不是让 trace 更多，而是让人真正看得懂。
- 只给技术解释会让多数用户无从判断；只给口语解释又不够审计和调试。

备选方案：

- 只保留 decision trace，由界面自行缩写展示。

不选原因：

- trace 更适合审计，不适合承担“用户下一步怎么做”的主入口职责。

### 3. “停下”必须是显式语义，不再只是零散状态组合

决定：

- runtime 对 workflow 停止或暂停的原因给出稳定分类，例如：
  - 已完成
  - 失败
  - 等待用户输入
  - 等待审批
  - 被策略阻断
  - 达到自动推进预算
  - 需要人工升级处理

同时提供与该分类配套的下一步建议。

原因：

- 现在用户往往只能从 `selected_action`、`pending_interrupts`、`status` 等字段拼出系统为什么停。
- Phase 2 需要把“停下的语义”变成一等对象，否则后续增加更多动作后只会更难理解。

备选方案：

- 继续使用现有细碎状态，由 Host 界面做组合判断。

不选原因：

- 组合规则会散落在多个入口里，难以维护，也不利于测试。

### 4. 信任与审批策略继续归 runtime 所有，但必须变得可解释

决定：

- policy 仍由 runtime 决定，Web/CLI 只展示结果和原因。
- trust policy 不只暴露少量固定档位，首版就允许项目级配置更细的规则。
- gate 除了风险等级和策略原因外，还要补充更直白的审批说明，例如“这是高成本远程计算，所以需要人工确认”。
- 对无需审批的动作，也允许 runtime 给出“为什么可以直接继续”的策略说明。

原因：

- 审批逻辑如果分散到界面，就会出现一边能执行、一边要求审批的错误。
- 用户不仅需要知道“要不要批”，还需要知道“为什么这次和上次不一样”。

备选方案：

- 保持现有 gate 数据结构不变，只在 UI 做文案包装。

不选原因：

- 这样解释无法进入 canonical state，也无法被 CLI、Web、测试和审计共享。

### 5. 进度只做“可行动的进度”，不做伪精确进度条

决定：

- 首版进度摘要聚焦以下内容：
  - 已完成什么
  - 当前正在做什么或卡在哪里
  - 下一步准备做什么
  - 还缺什么输入
  - 是否建议用户现在介入
- 首版不引入“预计还需多久”的明确字段。

原因：

- 当前 workflow 是持续决策型，不是固定流水线，伪装成精确百分比很容易误导。
- 对用户最有价值的不是“42%”，而是“系统现在在等审批”或“缺 ligand 输入，补这个后可继续”。

备选方案：

- 给每个 episode 做统一百分比进度条或剩余时间预估。

不选原因：

- 在 Phase 2 这个阶段，数据基础还不足以支撑可信的精确估计。

## Risks / Trade-offs

- [风险：状态字段变多，模型和 UI 都更复杂] → 用少量稳定字段承载体验摘要，避免把每个中间推理都写成新状态。
- [风险：口语解释和技术事实不一致] → 两层解释都由 runtime 同源生成，并把关键策略原因保留在 canonical state。
- [风险：用户把“下一步建议”误解为系统承诺] → 文案上明确区分“建议下一步”与“保证下一步”。
- [风险：不同停止原因之间边界模糊] → 先收敛少量稳定的终止分类，避免一开始设计太细。
- [风险：CLI 和 Web 的展示密度差异过大] → 用同一份结构化摘要，CLI 走简版，Web 走展开版，但语义一致。

## Migration Plan

1. 先在 `host-agent-planning` 中补齐终止分类、解释模型、进度摘要和可解释 policy 的规范要求。
2. 在 runtime 中以向后兼容方式增加这些结构化字段，保留现有状态字段不立即删除。
3. 更新 Web Host，把主操作区优先切换为“当前状态 + 为什么停 + 下一步建议”。
4. 更新 CLI，让 `status` 和 workflow 相关命令输出更简洁的进度与解释摘要，并在详细模式下展开技术说明。
5. 补回归测试，确保同一 episode 在 Web 与 CLI 上看到相同的停止原因、下一步建议和审批解释。

回滚策略：

- 新字段采用附加方式写入；若展示层出现问题，可先隐藏新摘要字段，保留原有 workflow 主路径不受影响。

## Resolved Decisions

- 首版不提供“预计还需多久”的明确字段，只提供当前阶段、当前卡点和下一步提示。
- trust policy 首版允许项目级配置更细规则，而不是只暴露少量固定档位。
- `plain_language_explanation` 首版固定使用中文，先保证一致性和可读性。
